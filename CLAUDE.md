# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`@czfabrics/front-ready` is a CLI (and a tiny library surface) that builds a static frontend and
deploys it to an S3 bucket. It ships three commands: `create` (make + configure the bucket for
static website hosting), `check` (validate config, bucket existence, content-hashing assumptions)
and `deploy` (build, then upload).

Package manager is **Bun** (`bun.lock`); the `build` script chains sub-steps with `bun run`.

## Commands

```sh
bun install
bun run dev <create|check|deploy>   # run the CLI from source (tsx main.ts) against the cwd's frontready config
bun run typecheck                   # tsc --noEmit, the only "lint" in this repo
bun run format:all                  # prettier --write (printWidth 90, no semis, single quotes)
bun run build                       # rimraf .dist → regenerate index.ts → esbuild → .d.ts → tsc-alias
bun run generate:readme             # regenerate README.md from .docs/*.md
bun run check:type-perf             # tsc --generateTrace + analyze-trace, for type-checking slowness
```

Tests use Vitest, configured in `vitest.config.ts` with `watch: true` and
`expect.requireAssertions: true` (a test with zero assertions fails).

```sh
bun run test                        # watch mode
bunx vitest run                      # single pass (CI-style)
bunx vitest run src/helpers/file.test.ts          # one file
bunx vitest run -t "name of the test"             # one test by name
bun run test:coverage
```

Note: **no test files exist yet**. The vitest project is wired (including `tsconfig.alias.json`
path resolution via `vite-tsconfig-paths`), so new `*.test.ts` files next to the code will be picked up.

## Generated files — do not edit by hand

- `README.md` — generated by `@appnest/readme` from `.blueprint.md` + `.docs/{1-overview,2-installation,3-quick-start,4-usage}.md`.
  Edit the files in `.docs/`, then run `bun run generate:readme`. This also runs on `prepublishOnly`.
- `index.ts` — regenerated by `vscode-generate-index-standalone` as the first step of `bun run build`.
  It is the package's public API surface (currently just `Config`).
- `.dist/` — build output, gitignored.

## Import aliases

All internal imports use `#<folder>/<file>` subpath aliases declared in `tsconfig.alias.json`
(e.g. `#use_cases/deploy_on_bucket`, `#helpers/effect`). **Adding a new top-level folder under
`src/` requires adding its alias there** — `tsconfig.alias.json` is the single source consumed by
`tsconfig.json`, by `vite-tsconfig-paths` for tests, and by `tsc-alias` to rewrite the emitted
`.d.ts` (`prepare:imports`). esbuild resolves them through `tsconfig.json`.

Compiler is strict with `noUncheckedIndexedAccess`, `noUnusedLocals`, `noUnusedParameters`
(`tsconfig.compiler.json`), so indexed reads are `T | undefined` — the code uses `!` or `Option`
rather than loosening the flag.

## Architecture

Everything runs inside **Effect** (effect-ts v3). `main.ts` wraps `cmd-ts`' `run()` into an Effect
and hands it to `NodeRuntime.runMain` with `NodeContext.layer` (which supplies `FileSystem`, `Path`
and `Command` from `@effect/platform-node`).

The three commands in `src/cli/` are structurally identical; copy one when adding a fourth:

1. `Layer.succeed(CliCommandContext, { commandName })`.
2. `startCli()` prints the intro banner and loads config (`c12` finds `frontready.config.*` in the
   user's cwd, then `ConfigSchema.safeParse` from `src/config/schema.ts` applies defaults).
3. Build two layers from the parsed config: `InternalConfigContext` (raw validated config) and
   `makeFrontDeploymentContextLayer(config)`.
4. Run the use case via `runAndInterruptOnCtrlC`, with `Effect.onInterrupt` → `cancel(...)` and
   `Effect.catchAll` → log + `outro(...)`. Commands never throw; they always end on an outro.

### The two config shapes collapse into one context

`src/factories/front_deployment_context.ts` is the key file. It `Match`es on `config.front.type`
and produces a single `FrontDeploymentContext` — `{ command, bucketName, buildOutputPath,
buildOutputHashing }` — so nothing downstream knows whether the project is Angular or custom:

- `custom`: command and output path come straight from config; `buildOutputHashing` is `undefined`
  (hence `check`'s "unable to determine" warning).
- `angular`: `src/helpers/angular.ts` parses `angular.json` with a tolerant Zod schema (supports both
  `architect` and `targets`, both the string and the `{ base, browser }` forms of `outputPath`, and
  the `:application` builder's implicit `/browser` suffix). If `configurationName` is absent from
  config, this factory interactively prompts for one and mutates `config.angular.configurationName`.

The bucket name is always `${namePrefix}-${configurationName | environmentName}`
(`src/factories/bucket_name.ts`), i.e. one bucket per environment.

### Layer stack

`FrontFileObjectService` (`src/front/service.ts`) is the single facade the use cases talk to. It
derives `FileRepositoryContext` (`cwd` = build output path) and `FileObjectBucketContext`
(bucket name + region) from `FrontDeploymentContext`/`InternalConfigContext` and provides them to:

- `FileRepository` (`src/file/repository.ts`) — recursive `FileSystem` walk producing `FileItem`s.
- `FileObjectRepository` (`src/file_object/repository.ts`) — all AWS SDK S3 commands, over an
  `S3Client` built in `src/file_object/api_instance.ts` from `config.bucket.params`.

Services are `Effect.Service` classes; a use case declares `dependencies: [FrontFileObjectService.Default]`
and the command provides `UseCase.Default` plus the two config-derived layers.

### FileItem / FileTree

`src/file/types.ts` defines two structurally-typed, symbol-branded values implementing `Equal`/`Hash`
(hashed by `absolutePath`) and `Iterable<FileItem>`. A `FileItem` iterates to itself; a `FileTree`
iterates to its items. `FileComponent = FileTree | FileItem`, so UI and upload code can treat a
single root-level file and a whole top-level folder uniformly — that's what
`listFrontBuildFileByRootComponents()` returns (grouping by first path segment), and what gives the
deploy UI one progress group per top-level folder.

### Deploy ordering invariant

`DeployOnBucketUseCase` uploads everything *except* the index document first (grouped,
concurrency from `config.bucket.upload.concurrency`), then uploads the index document alone.
`pickIndexDocument` in `src/helpers/file.ts` splits it out. This is deliberate: the new
`index.html` must only become reachable after the hashed chunks it references exist. Preserve it.

Content type comes from `mrmime` on the extension; `Cache-Control` from the first matching regex in
`cacheControlMapping`, else `defaultCacheControlValue` (`detectAndFillCacheControl`).

## Conventions

**Errors** — every failure is a `Data.TaggedError` in `src/errors/`, carrying structured context
(the S3 command, the file, the config section). Several override the `message` getter to render
nicely (e.g. `z.prettifyError`). `src/errors/interop/` holds the wrappers used specifically at
third-party promise boundaries (c12, clack, mrmime); keep that distinction when adding one.

**Promise → Effect** — never call `Effect.tryPromise` directly. Use `toEffect(promise, ErrorClass,
extraData)` / `toEffectSync(fn, ...)` from `#helpers/effect`, which maps the rejection into a tagged
error with its context attached.

**`genFn`** — `#helpers/effect`'s wrapper for generator functions that take arguments; it infers
`Effect<A, E, R>` from the yielded effects where a bare `Effect.gen` closure can't. Used throughout
services and helpers.

**UI** — `src/ui/` wraps `@clack/prompts` into Effects: `genConfirmUi`, `genSelectUi`, `genLoaderUi`
(spinner + timing + `process.exit` interception so a cancelled child process still stops the
spinner), `genCommandUi` (`genLoaderUi` over a shell command, streaming stdout/stderr into the
spinner message, failing on non-zero exit) and `genTaskLogsUi` (nested per-group task logs with
bounded sub-task concurrency). Use case code should go through these rather than calling clack.

**Cancellation** — "the user said no" is modelled as `Effect.interrupt`, not an error; the command
wrapper turns it into a `cancel(...)` outro. `runAndInterruptOnCtrlC` races the work against a raw
keypress listener because clack's prompts take over stdin.

**Style** — `function` expressions assigned to `const` rather than arrow functions for exported
top-level helpers; no semicolons; prettier `printWidth: 90`.
